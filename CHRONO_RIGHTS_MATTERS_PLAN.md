# Plan: chronology engine, Arts Rights Register, Matter Dashboard

The plan for the chronology, rights and matters work (approved after Phase 0; Phase 1 is done). It runs on the branch `feature/chronology-rights-matters` of `blursedperf/obsidian-legal-core`. The work began in the AGLC4 Citations repository and moved here when the two projects were separated (see the end of this plan).

## 1. Prerequisites (checked)

Legal Core 0.1.0 (API 1.0.0) is the starting point: the packages `ldm`, `md-pipeline`, `docx-engine`, `aglc`, `authority-store` and `legal-core-api`, the plugin in `src/`, and `examples/case-notes`. Its tests, golden exports and offline audit pass.

## 2. What the Obsidian API offers

**Bases.** Bases has a public plugin API (in the `obsidian` typings 1.14.4, which this repository uses):
- `Plugin.registerBasesView(viewId, { name, icon, factory, options })`, with `BasesView` (`onDataUpdated()`), `BasesQueryResult`, `BasesEntry` (one file per row, `getValue(propertyId)`) and `QueryController`.
- **Available since Obsidian 1.10.0,** with some members added in 1.10.2. It returns `false` when Bases is not enabled in a vault.
- **It is a stable, public API, but it doesn't fit everywhere:**
  - A Bases view renders **files and their properties**, so it would suit the rights register (one row per work or licence note).
  - It cannot express the chronology, whose rows are **list items inside notes**; the conflict analysis, which compares notes with each other; or the dashboards, which combine many sources.
  - Using it would also mean raising `minAppVersion` from 1.7.2 to 1.10, or detecting it at run time.
- **As the brief requires, every view is a custom `ItemView`.** A Bases view for the register could be added later, behind feature detection, without changing anything else.

**The metadata cache gives the indexes what they need without Dataview:**
- **`getFileCache(file)`:** frontmatter, `listItems` (with line positions, parents and task status), `blocks` (block ids), `links` and `sections`.
- **`metadataCache.on('changed', (file, data, cache))`:** passes the note's full text, so an incremental update needs no file read.
- **`on('deleted')` and `on('resolved')`,** plus `vault.on('rename')`.
- **`resolvedLinks`,** for backlinks. `getBacklinksForFile` is not public and is not used.

**Other constraints:**
- `app.plugins` is not public; plugins find each other through it (in one function) and through workspace events, as Legal Core does today.
- Workspace typings only list the built-in events, so custom events go through `Events`.

**The pure packages hold all the logic,** so the hard parts (dates, conflicts, chains of title, indexes, sorting, privacy redaction) are unit-tested without Obsidian. The plugins hold only Obsidian wiring and views.

**The new plugins need Legal Core at run time and depend on it only through its API** (`import type`), never by importing it:
- Each bundles the pure packages it uses: `precise-date` for display, `rights`.
- They export documents through Legal Core's engine, so they don't bundle `docx`, and should be small (an estimated 60–120 KB each).
- The standalone build guard applies to them too: at run time they load only what Obsidian provides.

**Releasing:** Obsidian lists one plugin per repository, so each new plugin will be released from its own repository, generated by an export script, as Legal Core is. Nothing is published in this work.

## 4. Dates with precision (`packages/precise-date`)

```ts
type Precision = 'year' | 'month' | 'day';

interface PreciseDate {
	/** First day covered, ISO YYYY-MM-DD: 2019 → 2019-01-01; 2019-03 → 2019-03-01. */
	start: string;
	/** Last day covered, inclusive: 2019 → 2019-12-31; 2019-03 → 2019-03-31; 2019-03..2019-05 → 2019-05-31. */
	end: string;
	/** Precision of the start, as written. */
	precision: Precision;
	/** Precision of the end, which may differ in a range ("2019-03-14..2019-05"). */
	endPrecision: Precision;
	/** True for "~2019-03"; for a range, if either end is approximate. */
	approximate: boolean;
	/** True when written as a range ("a..b"). A single month is not a range, although it covers one. */
	range: boolean;
}
```

**Accepted forms:**
- `2019`, `2019-03`, `2019-03-14`;
- ranges `2019-03..2019-05`, `2019..2021` and `2019-03-14..2019-04`;
- approximate forms `~2019-03` and `~2019..~2020`, with either end approximate;
- open-ended ranges `2019-03..` (no end) and `..2020` (no start), used for licence terms, with `end`/`start` of `null`.

**Rejected:** impossible dates (`2019-02-30`, `2019-13`), reversed ranges and malformed text. `parse()` returns `{ ok: false, reason }`, never throws, and never guesses.

**Changes from the brief, and why:**
- **`endPrecision` is added,** because a range can mix precisions.
- **`range` is added,** so a single month and a one-month range display differently.
- **`start` and `end` are both ISO days,** so comparisons are plain string comparisons. That's deterministic, and the inclusive end makes "a month covers the whole month" exact.

**Sorting is deterministic and honest:**
- Order by `start`, then `end` (the shorter span first), then precision (day before month before year), then title, then id.
- So `2019-03-01` sorts before `Mar 2019` (both start 1 March; the day ends first), and `Mar 2019` sorts before `2019-03-14`.
- **A month is never placed at a made-up day.** A view that lays dates out on a time axis draws a month as a span across it.

**Display matches the precision**, in Australian style:
- `14 Mar 2019`, `Mar 2019`, `2019`;
- `Mar–May 2019`, `14 Mar – Apr 2019`, `2019–2021`;
- `Mar 2019 (approx.)`, `from Mar 2019`, `until 2020`.

## 5. Events (`packages/chronology`, served by Legal Core)

```ts
interface LegalEvent {
	/** Stable: see below. */
	id: string;
	date: PreciseDate;
	title: string;          // Markdown, as written (links kept)
	parties: string[];      // link targets (paths of notes, resolved where possible)
	works: string[];
	matter?: string;
	source: { file: string; line?: number; ref?: string };
	confidence: 'confirmed' | 'probable' | 'unverified';
	kind?: string;
	track?: string;
	/** The extension that contributed it: "inline" for inline syntax, or an extension id. */
	contributedBy: string;
	/** True for events derived from sensitive data (ICIP): never shown without privacy checks. */
	sensitive?: boolean;
}
```

**Changes from the brief, and why:**
- **`parties` and `works` are always arrays,** possibly empty, so callers need no checks.
- **`sensitive` is added,** to carry the ICIP rules through every view and export.

### Inline syntax (final)

```markdown
- 2019-03-14 :: Demo recorded [[Song X]] {track=client conf=confirmed ref="CB 45"}
- ~2019-03 :: First draft of the lyrics shared with [[Jo Rivers]] {kind=creation}
- 2019-03..2019-05 :: Recording sessions at [[Harbour Studio]] {conf=probable}
- 2021-06-30 :: Option to extend expires {kind=option-deadline matter="[[2026-014 Film option]]"}  ^opt1
```

- **The shape:** a list item (`-`, `*` or `+`, at any indent) whose text starts with a date, then ` :: `, then the title, then optionally `{key=value …}` at the end. That's readable Markdown, and Obsidian shows it as an ordinary bullet. It also doesn't clash with Dataview's `key:: value` fields, which have no date before the `::`.
- **Attributes:**
  - `track`;
  - `conf` (`confirmed`, `probable` or `unverified`; default `unverified`);
  - `ref` (a source reference such as `CB 45`);
  - `kind`;
  - `matter`, `work` and `party` (each a link, and `work`/`party` may repeat).
  - Values with spaces take double quotes. An unknown attribute is kept, unused, and reported in the view, never silently dropped.
- **Links in the title** are read too. A link to a note with `type: work` is a work; one to a `type: client` note, or any other person or organisation note, is a party; one to a `type: matter` note is the matter.
- **The matter** is, in order: `matter=`, a link to a matter in the title, then the matter whose folder the note is in.
- **Which list items count:** only list items that match the shape. A date without ` :: ` is an ordinary list item, so no existing note is affected.

### Stable ids

- With a block id (`^opt1`): `<path>#^opt1`. This is stable through any edit, so it's recommended for events referred to elsewhere.
- Otherwise: `<path>#e-<hash of date and title>`, plus `-2`, `-3` … for exact duplicates in the same note. That's stable when other lines move, and changes only when the event itself is edited.
- Events from an extension get `<path>#<extension id>:<field>`, eg `Licences/L-2019-04.md#au-arts-rights:option-1-deadline`.
- On rename, ids are re-keyed to the new path, and subscribers are told: events from the old path removed, those under the new path added.

### Event sources

```ts
interface EventSource {
	id: string;                    // the extension id
	/** Events for one note, from its frontmatter (and text, if needed). Called on every change. */
	events(note: { path: string; frontmatter: Record<string, unknown> | undefined; text?: string }): EventInput[];
	/** Only notes with these `type` values are passed (fast filtering); none means every note. */
	types?: string[];
}
```

## 6. Note types (frontmatter; every note has `type`)

All the keys below are snake_case, as in the brief. Links are wikilinks in properties (`"[[Jo Rivers]]"`).

- **`type: client`:** `name` and `kind` (`individual` or `organisation`). Matters, works and agreements are found from links.
- **`type: work`:**
  - `title`, `creators` (links), `created` (a precise date), `made_public` (a precise date) and `medium`;
  - `client` (a link) and `icip` (a flag);
  - `resale_royalty_eligible` (`true`/`false`; when absent, the plugin suggests it for visual media);
  - `resales` (a list of `{ date, price_incl_gst, seller, buyer }`);
  - `icip_permissions` (the stub, see section 9).
- **`type: licence`:**
  - `works` (links), `licensor`, `licensee`, `rights` (a list), `media` (a list), `territory` (a list) and `exclusive`;
  - `start` and `end` (precise dates; `end` empty means no end);
  - `fee`, `royalty`, `options` (a list of `{ description, deadline }`) and `reversion` (a precise date, or a description);
  - `source_agreement` (a link) and `supersedes` (a link to a licence this one replaces).
  - The type also covers **assignments**, with `grant: assignment`; the default is `grant: licence`. Assignments are part of a chain of title.
- **`type: matter`:**
  - `number`, `client` (a link), `matter_type` (`dispute`, `transaction`, `advice`, `clearance` or `other`) and `status` (`open`, `on-hold` or `closed`);
  - `responsible`, `opened`, `closed` and `retention_until` (dates);
  - `compliance { conflict_check, costs_disclosure, engagement_signed }`, each `true` or a date;
  - `works` (links) and `next_deadline` (a date, or found from the matter's events).

**Changes from the brief, and why:**
- **`media` and `territory` are lists,** because a licence often covers several.
- **`supersedes` is added,** so renewals don't show as conflicts.
- **`grant: assignment` is added,** for the chain of title.
- **`resales` lives on the work.**
- **`icip_permissions` is a nested object,** so the stub can change as ICIP law develops without renaming keys.

**Templates and commands:**
- **New client, work, licence and matter:** each creates a note from a template in a folder chosen in settings.
- **The templates themselves:** plain Markdown with frontmatter, kept in a templates folder the user can edit. They are created on first use, and never overwritten.

## 7. API additions (Legal Core 1.0 → 1.1: additive only)

```ts
interface LegalCoreApi {
	// … everything in 1.0, unchanged …
	readonly events: {
		query(q?: EventQuery): LegalEvent[];          // sorted as in section 4
		get(id: string): LegalEvent | null;
		subscribe(fn: (change: { added: LegalEvent[]; removed: string[] }) => void): () => void;
		/** True once the first full index of the vault is complete. */
		ready(): boolean;
	};
	registerEventSource(source: EventSource): () => void;
	/** Export a prepared document (eg a chronology table) through the engine. */
	exportDocument(doc: MdDocument, options?: ExportDocxOptions): Promise<Uint8Array>;
	readonly panels: {
		/** Contribute a panel to a view that accepts panels, eg "matter-dashboard". */
		register(panel: PanelSpec): () => void;
		list(view: string): PanelSpec[];
		subscribe(fn: () => void): () => void;
	};
	readonly privacy: {
		enabled(): boolean;
		set(on: boolean): void;
		subscribe(fn: (on: boolean) => void): () => void;
	};
}

interface EventQuery {
	matter?: string; work?: string; party?: string;
	from?: string; to?: string;                // overlapping the period, by precise-date rules
	kinds?: string[]; tracks?: string[]; confidence?: LegalEvent['confidence'][];
	includeSensitive?: boolean;                // default false
}

interface PanelSpec {
	id: string; view: string; title: string; order?: number;
	render(target: { path: string }, ctx: PanelContext): HTMLElement | void;
}

interface PanelContext {
	el: HTMLElement;
	core: LegalCoreApi;
	/** Blur a value when privacy mode is on: names, figures. */
	redact(text: string, kind: 'name' | 'money'): string;
	privacy: boolean;
}
```

**API version:** 1.0.0 → **1.1.0**. Every 1.0 member is unchanged, so plugins asking for `^1.0` keep working; the new plugins ask for `^1.1`. Any later additions bump the minor version again (1.2 …).

**Changes from the brief, and why:**
1. **Panels are registered with Legal Core, not with legal-matters.** The brief has `matters.registerPanel(…)`. If panels were registered with legal-matters, arts-rights would depend on legal-matters, and the two would depend on each other's load order. Through Legal Core, arts-rights needs only Legal Core, and legal-matters renders what is registered for `"matter-dashboard"` (and `"client-dashboard"`). **legal-matters also exposes `matters.registerPanel(p)` as the brief's shorthand,** forwarding to `core.panels.register({ ...p, view: 'matter-dashboard' })`.
2. **Privacy mode lives in Legal Core.** Every view, including arts-rights' register and Legal Core's chronology, must blur together and stay in step, and the setting must survive a restart. **legal-matters has the command and the toggle.** The indicator shows in each view, and in the status bar.
3. **`exportDocument` is added**, so chronologies and reports are built as the document model, not as Markdown that would need escaping. The model's tables gain optional column widths (court chronologies need a narrow date column); existing goldens are unaffected.

## 8. Indexing and performance

**What is indexed:**
- **Note types** (work, licence, matter, client), from the metadata cache's frontmatter alone. No files are read.
- **Inline events,** only in notes whose cached `listItems` include a list item that could be one. The text comes from the `changed` event (no read), and from a read only on the first full pass.
- **Event sources,** run on frontmatter, filtered by `types`.

**How it stays up to date:**
- **First pass:** once the layout is ready, the index is built in the background, in chunks of 200 files, yielding between chunks. Views say "indexing…" until it's done.
- **After that,** it updates incrementally:
  - `changed` re-indexes one note;
  - `rename` re-keys it;
  - `deleted` removes it;
  - `resolved` refreshes link resolution.
- **Lookups:** in-memory maps by matter, work, party and file, plus a sorted array per query result, built lazily and invalidated on change.

**No persistent cache in version 1:**
- Notes are the only source of truth, and the index is rebuilt at each start, which leaves nothing to go stale. The estimate for 5,000 notes is about 1–2 seconds in the background.
- If measurement shows it's needed, a cache can be added later, in `.legal-core/index-cache.json`, keyed by each note's modification time and size. Deleting it would only cost a full rebuild.

**Target: dashboard render under 200 ms after indexing, for 5,000 work and licence notes.**
- **Model building:** a benchmark test generates 5,000 work and licence notes (and their events), indexes them, and times building each dashboard's model: the register's rows, conflict detection, the portfolio's deadlines and a matter dashboard.
- **Budgets:** the test fails over 50 ms per model, leaving the rest of the 200 ms for drawing.
- **Conflict detection:** grouped by work, so it costs O(licences per work²), not O(all licences²).
- **Drawing:** long lists show the first 200 rows, then "Show more", so drawing time doesn't grow with the vault.
- **In Obsidian:** QA measures the dashboards in the fixture vault and a 5,000-note generated vault, with `performance.now()` in the view's debug line.

## 9. Arts Rights Register

**Conflict detection.** Two grants conflict when all of these hold:
- they're for the same work;
- at least one is exclusive (two non-exclusive licences never conflict);
- they overlap in rights, media, territory and term;
- neither supersedes the other.

How each overlap is decided:
- **Rights and media:** normalised to lower case and trimmed. `all` (or `all rights`, `all media`) overlaps everything; otherwise they overlap if any entry is shared.
- **Territory:** `worldwide` overlaps every territory. A small built-in table maps regions to countries: Australia, New Zealand, ANZ, UK, Ireland, EU and its members, US, Canada, North America and Asia-Pacific (and Australian states within Australia). A region overlaps its countries, and two countries overlap only if they're the same.
  - **Unrecognised territories** are compared by name, and the view says so ("compared by name"), rather than guessing.
- **Terms:** they overlap if they share any day, with precise-date rules:
  - a missing `end` runs indefinitely;
  - a missing `start` is shown as "start not recorded" and treated as overlapping, so the conflict is shown rather than hidden;
  - an approximate date is treated at its widest.
- **Display:** each conflict is shown side by side, with the overlapping rights, media, territory and period highlighted, and links to both licences.

**Tests:**
- open-ended terms on either side, and terms touching on one day;
- `worldwide` against specific countries, regions against their members, and countries against countries;
- `all` against specific rights;
- exclusive against non-exclusive, and two non-exclusive;
- `supersedes` chains;
- assignments against later licences;
- approximate dates and month-precision terms;
- unrecognised territories.

**Chain of title.** For a work, an ordered table with each row's source document:
- creation (from the work);
- assignments;
- licences;
- options (deadlines);
- reversions.

Rows are ordered by date with precise-date rules, and grouped in that order where dates tie. It's exported through `exportDocument`.

**Resale royalty.**
- **Constants in one module, each with its source:** the rate (5%) and the threshold ($1,000, including GST), from the *Resale Royalty Right for Visual Artists Act 2009* (Cth). The comment says they must be checked against current law before use.
- **For each recorded resale:** the price, whether it's at or above the threshold, and 5% of the price (shown in dollars and cents, rounded half up to the cent).
- **The UI always says** "Potential royalty only: verify eligibility with Copyright Agency". It draws no conclusion about eligibility, which depends on facts the plugin doesn't know.

**ICIP permissions (stub).** `icip_permissions: { consent_given_by, on_behalf_of, scope, conditions, restrictions, date }`, and the work's `icip: true` flag. They're handled under these rules, enforced in code and tests:
- **Dashboards and registers** show only a flag ("ICIP"), never the contents; in privacy mode even the flag is hidden.
- **Exports leave ICIP details out by default.** Each export has an "Include ICIP permissions" checkbox, off every time, with a warning when it's on.
- **No logging:** ICIP values are never written to the console or anywhere else.
  - The index keeps them only in the note-type record, and the record's `toString`/JSON for logging omits them.
  - A test checks that the logs written while indexing the fixture vault contain none of them.
- **Events derived from ICIP data** carry `sensitive: true`, and queries exclude them unless they ask.

**Event source.** Each work's `created` and `made_public` dates, and each licence's `start`, `end`, option deadlines and reversion, become events. They're of kinds `creation`, `publication`, `licence-start`, `licence-end`, `option-deadline` and `reversion`, linked to the work and the matter.

**Panels** (registered with Legal Core):
- "Works and rights" on the matter dashboard and the client dashboard;
- "Upcoming expiries and options" on the matter dashboard and the portfolio.

## 10. Matters

**Matter dashboard.** A header with the number, client, status, responsible person and the next deadline in bold, then:
- key dates;
- the documents and sent-versions log;
- open issues (unticked tasks in the matter's issues note, or tagged `#issue` in the matter's notes);
- the recent chronology;
- recent file notes;
- the compliance checklist, with missing items in red;
- extension panels, ordered by `order`.

**Client dashboard.** The client's matters, works and agreements (when arts-rights is installed) and a combined timeline.

**Portfolio view:**
- deadlines in the next 7, 30 and 90 days;
- licence and option expiries across all clients;
- matters with no activity for N days, where N is a setting (default 60). Activity is the latest change to any note in the matter's folder, or an event.
- retention dates due for review.

**Record as sent** (command, on an exported file):
- **Choose the matter:** found from the file's folder, or picked from a list.
- **Fill in a form:** recipient, date (default today) and version (default: one more than the last).
- **The snapshot:** the file is copied to `<matter>/Sent/<name> v<n> (<date>).<ext>` (the folder is a setting). An existing file is never replaced.
- **The log:** a line is added to the matter note's "Sent versions" section.

**Open matter:**
- **A form:** the number, client, type and responsible person.
- **A folder from a template:** the matter note, a file-notes folder, a chronology note, a drafts folder and an issues note.
- **The template:** a folder the user can edit; the built-in one is used when none is set.

**Close matter:**
- **A closure checklist,** such as: final account issued, file returned, conflicts register updated, the user's own items.
- **Retention:** `closed` and `retention_until` are set. **The retention period is a setting with no default**: until it's set, the plugin asks for a date and makes no claim about what the law requires.
- **Archiving:** optionally, the matter folder is moved to an archive folder.

**Privacy mode** (command and toggle):
- **Blurs** client names, financial figures and ICIP indicators in every dashboard, register and chronology view.
- **Persists** across restarts, in Legal Core's settings.
- **Shows an indicator** in each view's header and the status bar while it's on.

**Matter status report** (Word, through `exportDocument`): the status, key dates and next steps, and optionally a chronology excerpt. ICIP details are left out unless chosen for that export.

## 11. Chronology view (in Legal Core)

- **Single timeline:** a sorted list of events, with each date shown at its precision; approximate dates and ranges are marked. Each row links to its source line, opening the note at that line.
- **Two-track comparison:** parallel columns by `track` (for example client and respondent), aligned by date, with gaps where one side has nothing.
- **Filters:** matter, work, party, kind, confidence, track and period.
- **Exports, through the engine:**
  - a court-style chronology, a three-column table of Date, Event and Source/Ref;
  - the two-track comparison table.
  - Both get new golden tests.

**Metadata import (optional, Phase 4):**
- **Proposed dates:** for files the user selects, events are proposed from EXIF `DateTimeOriginal` (JPEG and TIFF, read in plain JavaScript) and from each file's modified date.
- **Never silent:** each proposal is `unverified` and labelled with its source ("EXIF DateTimeOriginal of IMG_0412.jpg" or "file modified date"). It's shown in a review list to accept or reject; accepting writes an inline event to a chosen note.
- **Not supported:** HEIC and PNG metadata, in version 1.

## 12. Constraints and how they are met

| Constraint | How |
| --- | --- |
| Legal Core's API unbroken | API changes are additive only (1.1.0, then 1.2.0); every existing golden must pass |
| Mobile-safe | No Node APIs (existing lint rule); `isDesktopOnly: false`; EXIF in plain JavaScript |
| Local only | The offline audit covers the new packages and plugins; each README says so |
| No Dataview | Indexes from `metadataCache` and vault events only |
| Notes are the source of truth | Indexes are in memory and rebuilt; no cache file in version 1 |
| ICIP sensitivity | Section 9: flag only, hidden in privacy mode, out of exports by default, never logged; tested |
| Each plugin works with only Legal Core | legal-matters needs only Legal Core; arts-rights only Legal Core (panels appear when legal-matters is installed) |
| Missing or old dependency | A clear notice ("needs Legal Core 1.1 or later"); the plugin stays idle and never crashes |
| No publishing | Local commits on `feature/chronology-rights-matters` only |

## 13. Risks

| Risk | Mitigation |
| --- | --- |
| The first index of a large vault is slow on phones | Chunked and in the background; views show progress; only candidate notes are read. Measured in QA |
| Inline syntax catches list items not meant as events | It needs a leading date and ` :: `; unmatched items are untouched. Tested against the existing fixtures and sample notes |
| Territory and rights vocabularies vary | Lists normalised; built-in territories; unrecognised ones compared by name and labelled |
| Users read conflict, term, deadline or royalty output as legal advice | "Not legal advice; verify dates and calculations" on those views, exports and READMEs; no eligibility conclusions |
| ICIP data leaks through a new view or log | One redaction helper used by every view; ICIP fields left out of the index's loggable form; tests on exports and logs |
| `app.plugins` (not public) changes | Lookup in one function per plugin; workspace events as the signal |
| Two plugins write the same note | Only the user's commands write notes (open, close, record as sent, accept proposals), and only after confirmation where anything is replaced |
| The Legal Core API grows too fast | Only the members above in 1.1; each later addition is a minor version, documented in API.md |
